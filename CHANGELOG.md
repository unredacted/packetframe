# Changelog

All notable changes to PacketFrame are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project
uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

The release workflow publishes the section for the tagged version as the
GitHub release notes. It refuses a tag whose version disagrees with
`VERSION` and the workspace `Cargo.toml`, or whose section is missing.
Every section heading must be exactly `## [X.Y.Z] - YYYY-MM-DD` or
`## [X.Y.Z] - UNRELEASED`. A final (non-prerelease) tag needs the dated
form. To cut a release, replace `UNRELEASED` with the date, then push
the tag. Only a pushed `v*` tag publishes; a manual workflow run is
always a dry run. Releases up to 0.2.7 predate this file; their
notes are on the [releases page](https://github.com/unredacted/packetframe/releases).
Versions 0.2.8, 0.2.9 and 0.2.10, which some code comments cite, never
shipped; that work is part of 0.5.0.

## [0.6.0] - UNRELEASED

### Upgrading from 0.5.0

- **`forwarding-mode custom-fib` is now `forwarding-mode packetframe-fib`.** The old name still parses and logs a deprecation warning naming the line; it will be removed in a later release. Update your config at your next edit.
- **Renamed metrics.** The counters `custom_fib_hit`, `custom_fib_miss` and `custom_fib_no_neigh` are now `fib_hit`, `fib_miss` and `fib_no_neigh`, so the textfile exports `packetframe_fib_hit_total` and so on. The mode label reads `packetframe_fib_forwarding_mode{mode="packetframe-fib"}`. Counter indices are unchanged. Update any alert or dashboard that matches the old names.
- **vpp-offload refuses a state file another account could have written.** Attach, `packetframe detach --all` and `detach --keep-vpp` now refuse `<state-dir>/vpp-offload.json` unless it and `state-dir` are owned by root and closed to group and others, every directory above is root-owned and closed or sticky, and no part of the path is a symlink. The packaged default (`/var/lib/packetframe/state`) passes, and so does any `state-dir` where `packetframe reconfigure` works today: the pid file's reader already applies the same directory rules. Check any other before upgrading: [the check and the fix](docs/runbooks/vpp-offload.md#attach-or-detach-refuses-refusing-vpp-offloadjson-).
- **vpp-offload keep rules now use RSS.** The first steer after the upgrade rewrites a steered port's keeps in place; nothing to do. Before **downgrading** below 0.6.0, run this release's `packetframe detach --all`: an older daemon cannot recognise an RSS keep as its own, so its teardown would leave the keeps in the NIC.
- **fast-path refuses to attach keepalived's dedicated VRRP link.** A config that `attach`es it no longer starts; the error names the line to remove. Routers without keepalived are unaffected. See the change below.

### Changes

- **fast-path refuses to attach a dedicated VRRP link.** Allowlisted traffic arriving on an attached port is forwarded without passing through netfilter. On an HA pair whose VRRP runs over a link of its own (UniFi OS's HA link, for one), the standby gateway's own traffic arrives on that link, so attaching it let the standby reach allowlisted prefixes past the active gateway's firewall. On one gateway that kept the standby connected to a tailnet whose control server sat in an allowlisted prefix. When the active gateway's tailscaled restarted, the standby took subnet-router primacy for the active gateway's own LAN prefixes, and the active gateway, accepting routes, sent its own LAN traffic into the tunnel until fast-path was detached. Startup now reads `/run/vrrp/keepalived.conf` and `/etc/keepalived/keepalived.conf` and, before anything loads or pins, refuses an `attach` that names a `vrrp_instance`'s interface when that interface carries none of the instance's virtual addresses, either directly or through a device stacked on it (a VLAN or a bridge over it). With no `interface`, the instance's interface is the one holding its `unicast_src_ip`. A missing file says nothing. An instance whose addresses sit on its own interface or on devices over it (the usual keepalived LAN gateway, a trunk carrying the VLANs) is not refused. Where reading the config needs keepalived's own state (a `@config-id` line, an undefined `$` substitution, `~SEQ`), or an address names a device that does not exist, startup logs a warning and refuses nothing. Single-line `$NAME=value` definitions are expanded; `include` directives are not followed.

- **New fast-path directive `wan-egress from <cidr> [from <cidr> ...] [keep <cidr> ...]`** (IPv4). On gateways that install the full BGP table into `main` and consult `main` before their own WAN policy rules, with NAT only on the WAN interfaces, private sources whose destination's best path was a peering interface left un-NATed and died. Traffic from the listed sources now skips `main` and continues with the platform's own WAN rules and NAT, except for kept destinations (RFC 1918, RFC 6598, link-local, every `allow-prefix` and `local-prefix`, plus any `keep`), which still use `main`. PacketFrame installs `ip rule` entries tagged `proto 199` just below `lookup main` (a goto past it, with a `lookup local` anchor when needed, which never matches because `local` was already consulted first; not a `nop`, because UniFi's udapi-server refuses to start while any rule has neither a table nor a goto, and a `nop` anchor from a pre-release build is replaced on the first pass), reconciles them at start, on reload, on rule changes and every 30 s, writes nothing when they are already in place, never touches a rule it did not create, and removes them on a full `packetframe detach`. They stay (and the next start adopts them) across `systemctl stop`, `detach --keep-vpp` and a circuit-breaker trip, because they serve kernel forwarding rather than XDP. New `wan-egress` status row, `packetframe_wan_egress_*` textfile gauges and a `wan_egress_repaired` event. See [WAN egress](docs/runbooks/packetframe-fib.md#wan-egress).
- **A restart no longer waits for the route source to replay the whole table** (fast-path, `packetframe-fib`). A clean stop (`systemctl stop`, SIGTERM) now writes the route mirror's route-source advertisements to `<state-dir>/fast-path-route-ledger.bin` (~14 bytes a route), and the next start seeds the mirror from it before the route source connects: the FIB is full within seconds instead of after the replay (about 11 minutes for 1.35M routes from FRR). Seeded routes go in as a session loss leaves them: the live session's re-advertisements confirm them (an identical one is no FIB write and no VPP delta) and its `InitiationComplete` removes what it no longer has. The stop writes it within a 5 s budget that covers the snapshot and the write together; a stop that runs out of budget (a wedged filesystem, say) leaves no ledger rather than a late one. The start consumes the file whether or not it uses it, and refuses it by name when the route source differs (including the `peer-from` ACL wherever no `peer-ip` pins the speaker), its oldest routes were last confirmed more than `max-age` ago (default 30 minutes), the clock moved, the file is damaged or of another format, `forwarding-mode` is not `packetframe-fib`, its ownership or permissions (or those of `state-dir` and its ancestors) show another account could have written it (`untrusted`), or it is larger than any FIB could produce (`too-large`); the last two before a byte of it is read. The completeness authority does not attest a seeded mirror until the route source's first route arrives, then checks at once rather than at its interval, so a fresh VPP's first steer no longer waits for the replay. `packetframe detach` removes the file; `detach --keep-vpp` keeps it. New directive `route-ledger on|off [max-age <seconds>]` (default on), a `route-ledger` status row, `packetframe_fib_route_ledger_*` gauges, and `route_ledger_preserved`, `route_ledger_seeded`, `route_ledger_refused` and `route_ledger_reconciled` events. A BMP station now asks the mirror at its own start, as it does at every other stream boundary, whether an earlier stream's routes remain. See [the route ledger](docs/runbooks/packetframe-fib.md#restarts-the-route-ledger).
- **An unsteered adopted VPP no longer waits for the route source's replay to verify** (vpp-offload). With a mirror seeded from the fast-path route ledger, the adopted resync diff now runs once the feed session is up in its first session and the completeness authority agrees with the mirror, instead of after the route source's whole replay has gone quiet. The replay's identical re-advertisements kept that gate loud for the replay's length (~11 minutes at 1.35M routes from FRR). A mirror that loaded from empty, one with no authority configured, or a seed whose route source reconnected still waits for the stream to go quiet, as before. Every adopted resync now drops the route deltas its walk supersedes, so VPP is sent only what differs from what it holds rather than the whole queued table again. A port that was not steered still steers only when its `steer` flag moves. `FeedLiveness` gains `mirror_seeded`, set by the fast-path when it seeds and cleared by the route source's first GC. See [the unsteered diff and a seeded mirror](docs/runbooks/vpp-offload.md#the-unsteered-diff-and-a-seeded-mirror).
- **`Module::breaker_tripping()`**, an additive trait method with a no-op default: the loader calls it on the circuit-breaker path just before `detach`, so a module can tell a breaker teardown from any other. fast-path uses it to keep its `wan-egress` rules on a trip.
- **A route-feed reconnect no longer deletes the `fallback-default` 0/0 or `local-prefix` host routes** (`packetframe-fib`). The stale-route sweep after a BGP or BMP reconnect covered every route in the FIB, including these, which the neighbour resolver injects and no session re-announces. Every reconnect therefore deleted the default and every host route whose neighbour entry the kernel had not updated in between, and FRR on UniFi reconnects at every config upload. Destinations only the default covered fell to the kernel path, and with vpp-offload VPP was told to withdraw its default as well, so it dropped steered traffic to them. A host route came back at the kernel's next update of its neighbour entry, the default only at a daemon restart. The sweep now covers the feed's own routes only. Feed peer ids are now also kept out of the resolver's id range by construction: they are hashes of fields the sender chooses (a BMP peer distinguisher, a BGP ASN), so a sender could search for one that read as the resolver's and exempt its routes from the sweep, or collide with an interface's local routes. See [forcing a route-source resync](docs/runbooks/packetframe-fib.md#force-a-route-source-resync).
- **The BGP feed session no longer drops when route processing falls behind** (`route-source bgp`). The listener sent its KEEPALIVEs and checked its hold timer from the loop that applies each UPDATE, so nothing went out while an apply was slow. During a full-table load on a CPU-saturated gateway on 2026-10-07, FRR heard nothing for its 90 s hold time, tore the session down with `Hold Timer Expired`, and sent the whole table again once it reconnected about five minutes later. KEEPALIVEs now come from a task of their own. packetframe's hold timer now runs only while it waits on the socket for FRR's next message: time spent behind on route processing, with FRR's messages queued unread, no longer counts as FRR being silent. A peer that really goes quiet still expires the session a hold time after packetframe catches up with what it sent. Because the session now stays up however slowly routes apply, FRR showing `Established` no longer says they are landing. The `InitiationComplete` sweep of routes the session has not re-sent now fires only once packetframe has read no UPDATE for 5 s and has found nothing left unread on the socket, and only after every UPDATE read before that has been applied. It used to time the 5 s from the last UPDATE applied, so a slow apply of 5 s or more read as a quiet peer and could trigger the sweep the moment it finished, ahead of the UPDATEs queued behind it or still unread, pulling not-yet-re-applied routes out of the FIB in the middle of a reload. See [the feed session drops during a full-table load](docs/runbooks/packetframe-fib.md#symptom-the-feed-session-drops-during-a-full-table-load).
- **Lost netlink notifications are re-read instead of silently missed** (fast-path's redirect-target watcher, neigh-snoop). The kernel drops a multicast notification its subscriber's receive buffer has no room for and reports the loss once (`ENOBUFS`). Both consumers ignored that report, so a port bounce or provisioning burst that overflowed them left their state stale until a restart or SIGHUP: links created meanwhile stayed out of the redirect maps (their traffic on the kernel path), and neigh-snoop's neighbour mirror kept flushed entries as resolved (coverage too high, gate participants that no longer resolve, re-seeds skipped). Each now re-reads what its subscription feeds after an overrun, and reads on from a fresh subscription opened before the dumps, so messages queued before the loss cannot undo the re-read — neigh-snoop re-seeding a bridge whose neighbour rows changed unheard; the redirect watcher reporting qualifying links left out of the maps as their own condition — refused with `E2BIG` (the maps are full; offered again when an eviction makes room) or failing any other way (retried every 5 s) — asks for a larger receive buffer, and counts overruns and re-reads: a `redirect-watch` status row (which also reports a watcher that has stopped, something nothing reported before) with `packetframe_redirect_watch_*` gauges, and a neigh-snoop `netlink` row while a re-read is owed or running with `packetframe_neigh_snoop_netlink_*`. A neigh-snoop install for an address its kernel mirror holds no row for is now written without `NLM_F_REPLACE`, so a mirror that missed a live entry (a neighbour dump taken during churn can skip one, and the kernel does not flag neighbour dumps as interrupted) can no longer overwrite the MAC it holds, a confirmed one included; an unresolved entry is still filled. Every netlink request in neigh-snoop, `wan-egress` and `anyip` is now bounded (30 s; a neigh-snoop coverage sample 120 s). A reply the kernel never sent used to hang the waiting task for good: the neigh-snoop engine loop (its health frozen on the last state), its installer, a `wan-egress` pass (and with it every later pass and reload), or the BGP listener's restart behind `anyip`. A connection whose request did not end in a clean reply is not used again; neigh-snoop's installer has a connection of its own; an `anyip` write whose reply was lost is looked up before startup fails on it; and a re-read in flight no longer holds up `detach`. A `wan-egress` pass that could not see the rules now reports how many are in place as unknown rather than zero. See [`pass_not_in_devmap` climbs](docs/runbooks/packetframe-fib.md#symptom-pass_not_in_devmap-climbs) and [neigh-snoop triage](docs/runbooks/neigh-snoop.md#triage-by-symptom).
- The custom-FIB runbook moved to [`docs/runbooks/packetframe-fib.md`](docs/runbooks/packetframe-fib.md).
- **Flow-export groundwork (development only; release builds unchanged).**
  - New `packetframe-flow-encode` crate: sFlow v5, NetFlow v9, IPFIX flows and IPFIX packet reports.
  - New `packetframe flow-synth` subcommand, behind the off-by-default `dev-tools` feature, which sends modelled telemetry to a collector.
  - What Akvorado and FastNetMon Community do with each format, and what that requires of the exporter, is in [collector evidence](docs/flow-export/collectors.md).
- **New `packetframe sampler` subcommand** (lab tooling for the upcoming VPP flow sampler; does nothing on a box without it). It has four commands:
  - `status`: a read-only look at the sampler's coverage, status and counters. It exits non-zero unless coverage is healthy.
  - `watch`: the one consumer. It drains the sampler's rings and reports per-stage counts, losses, sample-to-receipt latency, coverage and decoded 5-tuples, following the sampler across VPP restarts.
  - `configure` and `clear`: write or remove the sampler's `desired.conf`.
- **The fast path carries a packet sampler for flow export, off until configured.** The XDP and tc programs can select one packet in N per CPU, at a random gap averaging N, and hand its first bytes, its ports and its fate (passed, dropped, or redirect decided) to a reader through a new `SAMPLES` perf array. Each sample carries the rate it was drawn at, and a packet is emitted once however its forwarding ends. Nothing sets a rate yet (flow-export will), so release builds sample nothing. Two new counters, `sample_selected` and `sample_emit_failed`, read 0 until then. STATS grows by four slots; two of them are the sampler's per-CPU state and never appear as counters. Three new maps are pinned (`SAMPLE_CFG`, `SAMPLES`, `SAMPLE_SCRATCH`). As with any STATS change, restart with `systemctl stop packetframe`, `packetframe detach --all`, then `systemctl start packetframe`.
- **New module `flow-export` (experimental): sampled packets to sFlow collectors.**
  - fast-path's XDP and tc programs, and VPP's sampler plugin on the ports vpp-offload steers, sample one packet in `sample-rate` (default 1000). The module sends each sample's first `header-bytes` (default 128) as sFlow v5 to every `collector`, for example Akvorado (`kind stats`) and FastNetMon (`kind ddos`).
  - A port is one sFlow data source whichever paths sample it: one sequence, and one pool counting what every path could have sampled. That is its kernel `rx_packets` for its XDP or tc program (steered packets never reach that counter), plus VPP's own count of the packets it received on the port. So a collector scales correctly whether or not every sample arrives. Samples carry the rate they were drawn at, so a rate change on SIGHUP never mislabels samples already in flight.
  - A reload that changes `sample-rate` or `header-bytes` succeeds only once fast-path's sampler runs at the new values. One that cannot be applied changes nothing, fails the reload, and leaves the `sampling` row Degraded with the reason. VPP's plugin takes the new values from the next `desired.conf`, and the `vpp` row reads Degraded until it has.
  - Status shows a row per path (`xdp`, `tc`, `vpp`) with each port's coverage (starting, covered, degraded on loss, uncovered on heavy loss or a busy port that yields no samples). A VPP port is also uncovered while the plugin is unavailable or its interface is missing from VPP, and the `vpp` row leads with the plugin's own state: its epoch, the generation it applied of the one asked, and why it is not healthy. There is also a `sampling` row (over budget below 1:1000), and a row per collector, which reports local submission only: receipt is the collector's to confirm. A collector reads Degraded while its sends fail or while datagrams exceed its per-tick send budget. Metrics are under `packetframe_flow_export_`. `worker_up` reads 0 once the export worker stalls or panics, and the coverage gauges then read 0 too.
  - **VPP.** With `module vpp-offload` configured, flow-export owns the plugin's `desired.conf` while it runs, asking for every VPP port. `packetframe sampler configure` and `clear` are refused meanwhile, as is a second `sampler watch`. A VPP interface index means something only to the VPP process that assigned it, so a sample is read only through the port list of the process that wrote it. A sample from a restarted VPP that its new port list does not yet cover is counted as unmapped, never attributed to a port by guess. Like samples lost to full rings, unmapped samples degrade VPP's coverage and ride the next VPP sample's `drops`. A VPP port reads `starting` for 60 s rather than 30 s, since its interface appears only once VPP is up.
  - Requires `module fast-path` listed before it, and `module vpp-offload` too when present. A failure to start degrades the module and never stops forwarding. A panic in the export worker stops both samplers and says why in the `worker` row. Stopping the module (including `systemctl stop`) stops both samplers, and so does `packetframe detach --all`.
  - `packetframe sampler status` and `watch` judge VPP coverage Degraded while samples are lost to full rings (`status` over a quarter second, `watch` over each report), or while more than half the ring slots are queued unread.
- **vpp-offload prepares the VPP sampler plugin's place, and the arm64 package ships the plugin** (flow export; nothing samples until flow export is configured).
  - **The directory.** Before VPP can start, attach mounts a size-limited tmpfs at `/run/packetframe/vpp/sampler`, sized for the plugin's epochs at this VPP's thread count. It is unmounted when the resources are released, after VPP is gone; `--keep-vpp` and `systemctl stop` keep it with VPP.
  - **Ownership.** PacketFrame's mount carries a marker file whose token is recorded in `vpp-sampler-mount` beside the state file. Only the mount carrying that marker is unmounted or reused as PacketFrame's own. The record survives an older build rewriting the state file, so a downgrade cannot strand the mount. A mount that is already there is used only when it passes the plugin's own check with room for the epochs beside its other files, and is never mounted over or unmounted.
  - **Never fatal.** A directory that cannot be prepared leaves VPP attaching and forwarding as before. A new `sampler-dir` status row says why, and it never changes the module's overall health.
  - **Stale configuration.** Attach removes any `desired.conf` left in the directory, so the plugin stays off. If it cannot (another writer holds the lock, or the removal fails), the `sampler-dir` row reads Degraded and names `packetframe sampler clear`. After a daemon restart, re-run `packetframe sampler configure` for lab sampling.
  - **Loading the plugin.** startup.conf adds `/usr/lib/packetframe/vpp_plugins` to VPP's plugin path. A VPP that is adopted keeps the plugins it started with until it restarts.
  - **Packaging.** The arm64 `.deb` and the `aarch64-unknown-linux-gnu` tarball carry the plugin, built against and smoke-tested in the VPP that vpp-offload's `SOURCE.json` names. A different VPP refuses it and starts the same. The tarball's install steps in the README now include the plugin.
- **vpp-offload names its unresolvable routes.** The `fib-synced` and `fib-v6` rows, the verify summary and a refused first steer now name up to five unresolvable routes, then `+K more`. Each name gives the prefix, the next hop, the device the neighbour source reported, and the reason (`not a VPP port`, `no neighbour: the kernel has not resolved it`, `the router's own address`, and so on). A new `unresolvable_routes` event records the set whenever it changes, at most once a minute. Before this, `unresolvable=1` named nothing, and the fast-path dump could not show the route either. See [reading the names](docs/runbooks/vpp-offload.md#packetframe_vpp_routesstateunresolvable--0).
- **Routes that are the router's own are kernel-delivered, not unresolvable** (vpp-offload). Besides its connected subnets (#265), a route is now left out of VPP and counted in `packetframe_vpp_kernel_delivered_routes` in two more cases. One is a host route to one of the router's own addresses (a `/32` or `/128` on any device, such as a dummy or honeypot device) that no next hop of which reaches VPP. The other, IPv4 only, is a route via the router itself that the kernel's own FIB entry for exactly that prefix delivers locally or carries only out devices VPP cannot reach, such as a static `/32` via a tunnel. Those lookups are capped in count and in time per walk, and stop at the first one the kernel fails to answer. A next hop that is the router's address is still never enough on its own, so `next-hop-self` transit routes stay unresolvable. A route VPP can carry is never reclassified. Each v4 kernel-delivered prefix still needs a `steer-exempt` before a first steer. See [kernel-delivered routes](docs/runbooks/vpp-offload.md#kernel-delivered-routes-the-routers-own-never-unresolvable).
- **A stale incomplete verify is re-run once the table is clean** (vpp-offload). A verdict that failed only on unresolvable routes, unexempted kernel-delivered prefixes or an empty sample used to stand until the next restart, so `fib-synced` stayed Degraded after the cause had cleared. It is now re-run once, after the table has been clean for 10 s, at most every 5 minutes, and only while converged, idle and answering. The re-run refreshes what `fib-synced` reports and nothing else. It emits no supervisor event, never changes steering, and never steers a first attach. Its event carries `rerun: true`. See [the re-run](docs/runbooks/vpp-offload.md#the-re-run-a-stale-verdict).
- **fast-path labels the router's own addresses as `local` nexthops.** A routing daemon advertises the routes it originates with its own address as next hop, and the kernel never resolves a neighbour for that, so the once-a-minute `nexthops awaiting resolution` line reported those nexthops as pending and chronic forever on a healthy box. They are now named once in the journal as `local`, never re-probed, and left out of that line. A nexthop whose address moves onto the router while it is resolved is reset to the kernel path, and late neighbour events for it are ignored. Otherwise traffic is unchanged: XDP still passes it to the kernel, and the map layout and stats counters are untouched. See [local nexthops](docs/runbooks/packetframe-fib.md#local-nexthops-the-routers-own-addresses).
- **vpp-offload spreads exempt traffic over the PF's queues instead of pinning it to queue 0.** Keep rules (the built-in exemptions, every `steer-exempt` and the v6 keeps) delivered to PF queue 0, whose IRQ sits on cpu0 on every port. As exemptions grew into bulk traffic (NAT return paths, LAN subnets, IX LANs) all of it converged on one core: on a production gateway on 2026-10-07 cpu0 ran at 99% softirq while the other CPUs idled, the PF dropped up to ~3.9k frames/s, a directly connected next hop lost 30% of pings and transit BGP sessions fell. Three changes:
  - **RSS keeps.** A keep is now an RSS rule on the PF's default context (`context 0`), so its traffic is hashed across the queues like unsteered traffic. The driver is asked at run time, per port: a port whose driver refuses the RSS action, or reads it back without it, falls back to the queue-0 form, with a log line, a `keep_queue0_fallback` event and the reason in status. Queue-0 keeps from an older daemon are recognised as ours (audit, slot reuse, teardown) and rewritten as RSS keeps by the next steer.
  - **Queue-0 IRQ placement.** While a port's keeps pin to queue 0, its queue-0 IRQ is moved to a CPU of its own (never one of VPP's cores, an isolated CPU or cpu0). The prior affinity is recorded first, in `<state-dir>/vpp-queue0-irqs.json`, and restored when the keeps stop needing it, on the module's teardown, and by `packetframe detach`.
  - **Visibility.** A new `kernel-path` status row per steered port: the keep form, the queue-0 IRQ, and receive, queue-0 and drop rates from `ethtool -S`. It is Degraded, port named, when a port drops 100 frames/s or more. New gauges `packetframe_vpp_keep_rss`, `packetframe_vpp_keeps_observed`, `packetframe_vpp_queue0_irq_cpu`, `packetframe_vpp_kernel_rx_frames`, `packetframe_vpp_kernel_rx_drops`, `packetframe_vpp_kernel_rx_fps`, `packetframe_vpp_kernel_rx_drops_per_second` and `packetframe_vpp_kernel_path_dropping`, and a rate-limited `kernel_path_dropping` event.

  See [the kernel path for exempt traffic](docs/runbooks/vpp-offload.md#the-kernel-path-for-exempt-traffic), which also has the manual IRQ move for an emergency.
- **vpp-offload refuses NICs it does not support.** It drives Marvell OCTEON NICs (PF driver `rvu_nicpf`) only. On any other NIC, attach could get as far as creating a VF and binding it to vfio before failing, since VPP's `octeon` driver cannot take the device. Attach now checks every `port`'s driver before it touches any NIC, and refuses with one message naming each port that fails. `packetframe feasibility` reports each port as `vpp.<port>.driver`, and on a foreign NIC `vpp.steering.budget` reads `not planned` instead of judging a rule table the module would never program. Nothing changes on OCTEON. See [supported hardware](crates/modules/vpp-offload/README.md#supported-hardware).
- **vpp-offload reads its state file only if this daemon could have written it, and only up to a size bound.** `<state-dir>/vpp-offload.json` names the VPP process an attach adopts and a teardown may SIGKILL, the VFs and hugepages a teardown releases, the MCAM rules it removes, and the token the preserved route ledger must match. It was read with a plain open that followed a symlink at any component, read the whole file whatever its size, and checked neither ownership nor permissions. It is now read only when the file and `state-dir` are owned by the daemon's uid and closed to group and others, every directory above is root-owned and closed or sticky, and no component is a symlink. It is read only up to 16 MiB: the widest file the module can write is ~12 MB, and a real one is a few KB. A vpp-offload section may now declare at most 64 `port` lines (config validation refuses the 65th), so every file the module can write fits the bound; the reference NIC has six ports. All of this is judged on the open file before a byte of it is read, as fast-path's route ledger is. A refusal fails the attach, `packetframe detach --all` and the `--keep-vpp` preflight, with a message naming the fix (for ownership: `chown root:root`, and `chmod 755` on `state-dir`). It is never read as a fresh attach, because attaching over resources the file records would acquire them twice. That includes an untrusted `state-dir` with no file in it, which another account could have emptied. Attach now reads the file before it touches a NIC. Before, an unreadable file could surface as an MCAM budget refusal that blamed the allowlist, because planning had run without the module's own recorded rules. A reload still plans without an unreadable file, since a reload must stay a rollback lever, and logs a warning saying so. See [Attach or `detach` refuses](docs/runbooks/vpp-offload.md#attach-or-detach-refuses-refusing-vpp-offloadjson-).
- **vpp-offload writes its state file without following a symlink anywhere in `state-dir`.** `<state-dir>/vpp-offload.json` was written, renamed and removed by pathname, so a symlink at any component of `state-dir` chose where the daemon wrote or deleted it. A `state-dir` the save created was made under the umask, so a 002 umask left it group-writable, and the reader above then refused it at the next attach and at `packetframe detach --all`. It is now written, renamed and removed relative to a directory opened one component at a time without following symlinks, as the pid file and the route ledgers are, and a directory the save creates is never writable by group or others. A symlink or directory at `vpp-offload.json.tmp` now fails the save with a message naming it for removal, where before the save removed what was there and wrote in its place.
- **The other `state-dir` writers no longer follow a symlink anywhere in the path either.** fast-path's pin registry (`attachments.json`), `tc-links.json`, `anyip.lock` and circuit-breaker trip flag, guard's `guard-tc-links.json`, and neigh-snoop's per-bridge files and its load and feasibility probes of `persist-dir` were written by pathname. The registry and both tc-links records were removed that way, and the module health snapshot's `state-dir` was created that way. So a symlink at a temp name, at the trip flag itself, or at any component of the directory chose where the daemon wrote, created or deleted. They now go through the same no-follow walk as the pid file and vpp-offload's state file. A directory one of them creates is never writable by group or others: under a 002 umask, fast-path attaching first made a fresh `state-dir` 0775, which vpp-offload's state-file reader then refused. The files are now created 0600, as the pid file is. A symlink or directory at a temp name now fails the write with a message naming it. So does anything but a regular file at `anyip.lock`, where a FIFO used to stop the attach.
- **vpp-offload no longer reads a stall of its own supervision loop as VPP being wedged.** The loop that pings VPP also makes kernel calls that wait on `rtnl_lock`, and the silence clock ran on while it was blocked. After such a stall, one unanswered probe was enough to tear VPP down, with none of the tolerance the budget promises. A production gateway lost its steered VPP 18 s after the kernel appeared to release that lock from a ~40 s hold, and the eBPF tier then carried everything until the route mirror reloaded. A pass that arrives more than the wedge budget after the previous one, not counting time spent waiting on VPP's socket, now restarts the measurement. VPP is then called wedged only after a fresh probe and the full budget measured from the resume. The bound for a VPP that really hangs is unchanged while the loop runs (2 s when steered) and is measured from the resume after a stall. Time blocked on VPP's own socket is never excused, and a stall cannot erase more missed probes than the budget tolerates as jitter. A probe now reconnects first if something it did not hear about dropped the socket. Each reconnect gives up after 500 ms, the socket's own connect included; before, a connect into the full backlog of a VPP that had stopped accepting could block the supervision loop indefinitely. Any reply from VPP, such as a route batch or a verify probe, now counts as proof of life, so a VPP that keeps answering a long burst of route changes is not torn down because a ping queued behind them came back late. A VPP that answers nothing is held to the same bound. A wedge logs its evidence: silence, last probe error, time spent waiting on VPP, and the loop's longest gap. The `vpp_teardown` event carries the same as new fields. See [a teardown with `cause=Wedged`](docs/runbooks/vpp-offload.md#a-teardown-with-causewedged).
- **The fast-path neighbour resolver no longer hangs for good after a link flush, and no longer fails silently** (`packetframe-fib`). A configuration apply that toggled a member port and an IX bridge made the kernel flush every neighbour on them. The resolver's multicast socket overflowed, and a reply to one of its own netlink requests, which travelled over that same socket with no timeout, was dropped with the notifications. The loop then waited for it forever. The kernel had the nexthops REACHABLE, the FIB had 2 of 475 resolved, XDP forwarded nothing, and fast-path read healthy for more than thirteen minutes, until a daemon restart. Five changes:
  - Requests (route lookups, neighbour kicks, read-backs and the link, neighbour and FDB dumps) now go over a socket of their own, bounded at 5 s (10 s for a dump). A request that times out leaves its nexthop to the programmer's next re-probe and retires the socket. No second socket opens while a retired one is still blocked in the kernel, and probes skipped meanwhile are asked for again once one can.
  - An overrun on the multicast socket, where the kernel drops notifications, triggers a resync. The resolver re-reads links, neighbours and the bridge FDB and announces what changed, as the lost notifications would have.
    - The dumps are taken on a fresh subscription, and the overflowed socket is dropped with everything still queued on it. What it still held is older than what was lost, and replaying it after the dump would undo the dump. If nothing was applied, the old subscription is kept.
    - What the dumps list is applied first.
    - An entry missing from a dump is confirmed gone with a single-entry get before it is withdrawn, because a dump can skip a live entry. A neighbour on a device that no longer exists counts as gone, and a device's deletion takes any neighbours still held on it.
    - Each outcome is announced as the lost notification would have been. A neighbour now `FAILED` is announced `Failed` and keeps its local-prefix route. A neighbour that moved to another interface also loses its entry on the old one, which withdraws the host route it had there.
    - Confirmations stop once the request socket is retired and are capped at 2 s per read; the rest are owed to the next resync.
    - The receive buffer is raised to 16 MiB.
  - A probe suppressed on an `ix-mode` interface still reads the kernel's entry back. This is a unicast get, so nothing goes onto the fabric.
  - A supervisor restarts a resolver loop that exits with an error, or that makes no progress for 30 s outside a wait on the FIB programmer. Restarts back off from 1 s to 60 s. The new loop re-reads the kernel and announces the difference.
  - After a resync or a restart, the programmer brings every unresolved nexthop's next re-probe forward to now, instead of leaving it at a backoff that may have reached a minute. The backoff itself keeps counting.
  - New `neigh-resolver` status row (Unhealthy while the loop makes no progress or is between restarts, Degraded for ten minutes after a restart and while a resync is owed, with the reason in each case), new `packetframe_fib_neigh_resolver_*` counters and gauges, the same counters in the `neighbour resolver stats` line, and a `neigh_resolver_restarted` event.

  See [nexthops stuck `incomplete` while the kernel has them](docs/runbooks/packetframe-fib.md#symptom-nexthops-stuck-incomplete-while-the-kernel-neighbour-is-reachable).
- **vpp-offload reads a preserved route ledger only if this daemon could have written it, and only up to a size bound.** A `--keep-vpp` start adopts VPP's FIB from `<state-dir>/vpp-route-ledger.bin` without reading VPP, so a record another account could have written was a fabricated FIB the adoption trusted, and the file was read whole before any check, so a huge or sparse one could exhaust the daemon's memory. The start now refuses it before reading a byte when its ownership or permissions, or those of `state-dir` and its ancestors, show another account could have written it (`untrusted`, the check fast-path's route ledger makes), or when it is larger than the widest record this run's route capacity could encode to (`too-large`; about 500 MB at the default `expected-routes` with `v6 on`, against ~11 MB for a 1.09M-route table). Either refusal removes the file and takes the dump path, as every other refusal does; none fails the start. Every refusal at bring-up is now also recorded as `preserved_ledger_rejected`, with the check that refused it as its `stage` (`untrusted`, `too-large`, `unreadable`, `corrupt`, `format-version`, `unremovable`, `process`, `token`, `interfaces`); they were only in the journal before. A `state-dir` group or others can write now costs a keep-vpp restart its preserved ledger: fix its ownership and modes (`chown root:root`, `chmod 755`). See [the preserved route ledger](docs/runbooks/vpp-offload.md#what-a-keep-vpp-restart-costs-now-the-preserved-route-ledger).
- **A steer that diverts more traffic onto VPP waits until VPP has caught up with the route mirror and a verify covers the table** (vpp-offload). After a 2026-10-07 restart adopted a near-empty unsteered VPP, verify ran on one probe against a one-route table, and a lever move nine minutes later was admitted on that verdict while VPP held about 60% of the reloaded table.
  - **What is held.** The first steer, and equally a change that adds a port, prefix, direction or `v6-divert` to ports already steered (the next canary rung during a reload), widens a prefix, drops or narrows a `steer-exempt` or `steer-keep6` on a port that goes on diverting, or re-asserts rules a readback found wiped or a failed reconcile rolled out. It is judged by coverage against what the NIC is doing, after the IPv6 gate is set: a prefix narrowed inside one already diverted is not an addition. The lever, the module's retry and a convergence re-steering a remembered want all pass through it. A change that diverts the same or less, and `steer off`, are never held, and a held addition leaves the installed rules exactly as they are.
  - **Until when.** (1) The route changes still owed to VPP are no more than a quiet second's churn (64 on a small table, about 1,300 on a full one), no neighbour change is queued at all, and the last update landed. A next hop reporting a NUD transition with the same MAC is not a neighbour change. (2) The last verify drew the standard 64 probes, or the whole of a smaller table, from at least 90% of the IPv4 table installed now, and found no mismatch.
  - **What clears it.** A verdict the table has outgrown is re-run about ten seconds after VPP has caught up on routes, without the five-minute limit an incomplete one keeps unless the last re-run could not reach VPP, and the remembered want then steers on its own; the re-run's event carries a `cause`. A verdict that found a mismatch is never re-run (a new sample can miss the prefixes it caught), and a stopping daemon no longer preserves a route ledger any verify disproved in either family, an IPv6-only mismatch included, so a restart reads VPP's FIB and corrects it. On a box already steered that restart takes the read-back path, about three minutes unsteered on a full table. A port that was never steered needs its lever moved again after that restart.
  - **What you see.** The lever's refusal and the status rows name what it waits for, and say when waiting will not clear it. A hold is not a failure: a port already steered keeps its rules and its traffic on VPP, and the event log records `steer_held`, not `steer_failed`. A box in `steered` stays there, and the module's retry re-attempts the held change without the first-steer FIB gate, as the lever does for a steered port. A convergence's held re-assert waits in `ready` instead, with `packetframe_vpp_steered` still 1. `fib-synced` now reads `last verified on P probes against M routes`, and is Degraded while that verdict no longer covers the table.

  See [the first-steer hold](docs/runbooks/vpp-offload.md#the-first-steer-hold-vpp-caught-up-and-a-verify-that-covers-the-table).

## [0.5.0] - 2026-09-28

The first release since 0.2.7 (2026-05-20). It adds three modules (vpp-offload, neigh-snoop, and guard, which is experimental) and a persistent event log. No directive was removed and a 0.2.7 config parses unchanged, but read **Upgrading from 0.2.7** before installing: the upgrade order matters, and one default changed.

### Upgrading from 0.2.7

1. `systemctl stop packetframe`
2. `packetframe detach --all`, run with the **old** 0.2.7 binary. fast-path refuses to start over the pins a previous daemon left.
3. Install the 0.5.0 package or tarball.
4. `systemctl daemon-reload`. The .deb runs no maintainer scripts, so it neither reloads systemd nor stops or restarts the daemon.
5. `systemctl start packetframe`

- **Behaviour change: `bridge-resolve` now defaults to on (`auto`).** While the bridge short-circuit is installed, `mss-clamp … via <bridge>` no longer matches, because clamp matching keys on the resolved egress device. Scope the clamp `via` the underlying device, or set `bridge-resolve off` to keep 0.2.7's behaviour. The daemon logs a warning naming both when it sees this.
- **Installing the VPP package** (vpp-offload only): follow the [vpp-unifi](https://github.com/unredacted/vpp-unifi) README exactly. It ships a boot-time hugepage sysctl file that its skip flag does not remove. Delete the file and confirm it is gone before you reboot; `packetframe feasibility` flags it as `vpp.sysctl-hugepages`.
- **Downgrading:** run **0.5.0**'s `packetframe detach --all` before installing 0.2.7. 0.2.7's `detach` does not know guard's tc filters, VPP's MCAM rules, the IPv6 hand-back veth, tc-ingress attachments or the saved coalescing values, and leaves them in place.
- **Already on a main-branch build running vpp-offload:** install, `systemctl daemon-reload`, then `systemctl stop packetframe && packetframe detach --keep-vpp && systemctl start packetframe`; VPP keeps forwarding throughout. Before that, rename `v6-outbound` to `v6-divert` on any `port` line and drop any `steer-keep6 tcp 179 …` or destination-port `steer-keep6 tcp|udp 53` line (now built-in keeps); 0.5.0 refuses a config with either.

### Highlights

- **VPP offload, in production.** vpp-offload steers IPv4 and IPv6, in both directions, into a VPP instance on NIC virtual functions, with the eBPF fast-path as the failover tier. On the reference deployment (four steered ports, full IPv4 and IPv6 tables), softirq is about 74% of CPU with no bypass and 31–62% with the eBPF fast-path alone. Steering IPv4 into VPP took it to 11–19%, and moving IPv6 in alongside it took it to about 1%. Every figure from the fast-path-only one on is an off-peak reading. [Runbook](https://github.com/unredacted/packetframe/blob/v0.5.0/docs/runbooks/vpp-offload.md) · [Measurements](https://github.com/unredacted/packetframe/blob/main/docs/runbooks/vpp-offload.md#numbers-measured-vs-published-on-faith)
- **Restarts that stay steered.** `packetframe detach --keep-vpp` leaves VPP forwarding, and the next daemon adopts it from the route ledger the clean stop preserved. Measured on the reference deployment: no unsteered window, and VPP is never restarted. [Runbook](https://github.com/unredacted/packetframe/blob/v0.5.0/docs/runbooks/vpp-offload.md#what-a-keep-vpp-restart-costs-now-the-preserved-route-ledger)
- **neigh-snoop** learns neighbours on IX-facing bridges passively and feeds FRR's next-hop gate. In production on the reference deployment. [Runbook](https://github.com/unredacted/packetframe/blob/v0.5.0/docs/runbooks/neigh-snoop.md)
- **Event log.** `packetframe events` shows steering, verify, restarts and health transitions from a persistent log, with or without the daemon running. [Runbook](https://github.com/unredacted/packetframe/blob/v0.5.0/docs/runbooks/event-log.md)

### Changes

**vpp-offload** (new)

- Supervises a VPP process: startup config, core placement, IRQs moved off VPP's cores. Any VPP whose binary-API CRCs match is accepted at attach. ([#105](https://github.com/unredacted/packetframe/pull/105), [#121](https://github.com/unredacted/packetframe/pull/121), [#238](https://github.com/unredacted/packetframe/pull/238))
- Routes come from fast-path's resolved FIB, `fallback-default` included, with readback verify and a drift scan. ([#123](https://github.com/unredacted/packetframe/pull/123), [#266](https://github.com/unredacted/packetframe/pull/266))
- NIC MCAM steering per port: `port … steer on`, `direction src|dst|both`, trunks with `vlans all`, bridged VLANs through a BVI. `steer-capacity` enlarges the NIC's rule table. The steering lever reloads without a restart. ([#127](https://github.com/unredacted/packetframe/pull/127), [#128](https://github.com/unredacted/packetframe/pull/128), [#190](https://github.com/unredacted/packetframe/pull/190), [#249](https://github.com/unredacted/packetframe/pull/249), [#255](https://github.com/unredacted/packetframe/pull/255), [#258](https://github.com/unredacted/packetframe/pull/258))
- `steer-exempt` keeps chosen destinations on the kernel path; the exemption tripwire reports kernel routes VPP lacks, for IPv4 and IPv6. ([#189](https://github.com/unredacted/packetframe/pull/189), [#192](https://github.com/unredacted/packetframe/pull/192), [#281](https://github.com/unredacted/packetframe/pull/281))
- `local-route` / `local-route6` deliver traffic to hosts on attached VLANs. VPP resolves new neighbours itself (glean); glean and ARP-reply counters are exported. ([#190](https://github.com/unredacted/packetframe/pull/190), [#282](https://github.com/unredacted/packetframe/pull/282), [#287](https://github.com/unredacted/packetframe/pull/287))
- IPv6: `v6 on` loads the IPv6 table into VPP. `v6-divert <vlans>|untagged` on a `port` line diverts TCP and UDP over IPv6 addressed to the router's MAC. `steer-keep6` keeps services that accept new sessions on the kernel path; DNS (destination port 53) and BGP (TCP 179, both directions) are built-in keeps. ([#278](https://github.com/unredacted/packetframe/pull/278), [#279](https://github.com/unredacted/packetframe/pull/279), [#280](https://github.com/unredacted/packetframe/pull/280))
- Router-owned IPv6 that `v6-divert` sends to VPP returns to the kernel over a hand-back veth, guarded by a stateless ACL in VPP that admits only replies. ([#283](https://github.com/unredacted/packetframe/pull/283))
- `loopback-address6` gives VPP a global source for its ICMPv6 errors; `drift-accept6` acknowledges an IPv6 drift finding. ([#285](https://github.com/unredacted/packetframe/pull/285), [#288](https://github.com/unredacted/packetframe/pull/288))
- `packetframe detach --keep-vpp` restarts the daemon while VPP forwards. Without a usable route ledger the next start reads VPP's FIB instead, on the eBPF tier meanwhile (about 3 minutes at 1.1M routes); the `adoption_path` event says which path ran. ([#253](https://github.com/unredacted/packetframe/pull/253), [#277](https://github.com/unredacted/packetframe/pull/277))
- Per-port health rows in `packetframe status`, gauges in the metrics textfile, and remedies that name commands the module accepts. ([#114](https://github.com/unredacted/packetframe/pull/114), [#129](https://github.com/unredacted/packetframe/pull/129))

**neigh-snoop** (new)

- Learns third-party ARP/ND pairs on IX-facing bridges from a receive-only socket, installs them as `NUD_STALE`, and never overrides a confirmed entry. ([#212](https://github.com/unredacted/packetframe/pull/212), [#218](https://github.com/unredacted/packetframe/pull/218), [#215](https://github.com/unredacted/packetframe/pull/215))
- Persists its table per bridge (`persist-dir`, `seed-max-age`) and picks up a recreated bridge by name. ([#217](https://github.com/unredacted/packetframe/pull/217))
- `bridge <iface> ix-mode` stops fast-path's resolver sending proactive probes on that bridge. ([#213](https://github.com/unredacted/packetframe/pull/213))
- `frr-gate` reconciles FRR's next-hop prefix-lists from what was learned and measures route-server coverage. ([#216](https://github.com/unredacted/packetframe/pull/216))

**guard** (new, experimental)

- A tc-egress frame policer for IX-facing interfaces: per-target ARP/NS rate limit, LLDP drop, foreign-source-MAC drop and a broadcast/multicast catch-all, each class `monitor` or enforce. **Not validated on the reference vendor kernel**; run every class in `monitor` first. ([#204](https://github.com/unredacted/packetframe/pull/204)–[#207](https://github.com/unredacted/packetframe/pull/207), [runbook](https://github.com/unredacted/packetframe/blob/v0.5.0/docs/runbooks/guard.md))

**fast-path**

- `integrity-authority birdc [path] | frr upstream <ip> … | none` names what attests the route mirror is complete. The default is the local `birdc`, as in 0.2.7; `frr` reads FRR 10 through `vtysh` on a configurable `interval`. Restart-only. ([#173](https://github.com/unredacted/packetframe/pull/173), [#232](https://github.com/unredacted/packetframe/pull/232), [#236](https://github.com/unredacted/packetframe/pull/236))
- `route-source bgp … anyip` listens on a phantom address, so FRR can feed routes over iBGP from a non-loopback address. ([#196](https://github.com/unredacted/packetframe/pull/196))
- `bridge-resolve auto|on|off`: bridge egress short-circuit, on by default (see Upgrading). ([#78](https://github.com/unredacted/packetframe/pull/78))
- `fdb-pin on`: FDB-pinned direct-to-port egress through a multi-member bridge. Opt-in, restart-only. ([#85](https://github.com/unredacted/packetframe/pull/85))
- `fib-cache on`: a destination cache in front of custom-FIB lookups. Default off. ([#79](https://github.com/unredacted/packetframe/pull/79))
- `coalesce …`: NIC interrupt coalescing at attach, restored by `detach`. Restart-only. ([#269](https://github.com/unredacted/packetframe/pull/269))
- `local-prefix6`: the connected fast path for IPv6, with NDP kept off it. ([#72](https://github.com/unredacted/packetframe/pull/72))
- `attach <iface> tc`: a tc-ingress datapath (custom-fib only). It measured about 70% more CPU per packet than generic XDP on the reference hardware, so it is not recommended. ([#75](https://github.com/unredacted/packetframe/pull/75))
- New counters: the softnet `time_squeeze` export, and `err_parse_tc` split by bounds check. ([#184](https://github.com/unredacted/packetframe/pull/184), [#138](https://github.com/unredacted/packetframe/pull/138))

**probe** (`packetframe feasibility`)

- `vpp.sysctl-hugepages` detects a boot-persistent hugepage sysctl, priced at the running kernel's page size. It is a rollout gate with its own verdict bucket. ([#201](https://github.com/unredacted/packetframe/pull/201), [#225](https://github.com/unredacted/packetframe/pull/225))
- Flags per-packet IRQ coalescing. ([#84](https://github.com/unredacted/packetframe/pull/84))

**CLI and operations**

- The event log (`packetframe events`) is on by default at `<state-dir>/events.log`; `event-log <path>|off` and `event-log-max <size>` change it. ([#289](https://github.com/unredacted/packetframe/pull/289))
- The systemd unit caps the restart loop (`StartLimitBurst=3` in 300 s), sets `KillMode=process` so a stop does not kill a VPP kept for adoption, and adds `LogsDirectory=packetframe`. ([#224](https://github.com/unredacted/packetframe/pull/224), [#242](https://github.com/unredacted/packetframe/pull/242))
- Restart-required refusals quote the full restart command. ([#273](https://github.com/unredacted/packetframe/pull/273))
- Release artifacts include `CHANGELOG.md`, `conf/example.conf` and the runbooks. ([#294](https://github.com/unredacted/packetframe/pull/294))
- Built with Rust 1.98.1; building from source needs 1.98 or later. ([#296](https://github.com/unredacted/packetframe/pull/296))

**Fixes**

- fast-path routes only frames addressed to the router. ([#271](https://github.com/unredacted/packetframe/pull/271))
- fast-path re-probes lost nexthops and tracks redirect targets live, and `status` no longer hides traffic that takes the kernel path. ([#220](https://github.com/unredacted/packetframe/pull/220))
- The anyip reconcile no longer dumps the whole FIB, and failed custom-FIB deletes are repaired. ([#223](https://github.com/unredacted/packetframe/pull/223), [#154](https://github.com/unredacted/packetframe/pull/154))
- A vpp-offload failure degrades that module and leaves fast-path running. ([#237](https://github.com/unredacted/packetframe/pull/237))
- `status`, `reconfigure` and `detach` recognise a running daemon when run from a newly installed binary; `detach` no longer proceeds under a live daemon. ([#164](https://github.com/unredacted/packetframe/pull/164))
- `log-level` takes effect and reloads with SIGHUP; 0.2.7 parsed it and ignored it. ([#169](https://github.com/unredacted/packetframe/pull/169))

### Known limitations

- A fast-path restart still bounces the link on drivers where XDP attach and detach reset the port (a few lost pings over about two minutes on the reference hardware), because fast-path does not adopt pins across a restart.
- IPv6 is steered by frame, not address: only TCP/UDP arriving on a VLAN listed in `v6-divert` is offloaded, so list every upstream VLAN. The allowlist does not scope what is diverted, and diverted IPv6 bypasses the kernel's forward-path netfilter. ([runbook](https://github.com/unredacted/packetframe/blob/v0.5.0/docs/runbooks/vpp-offload.md#v6-divert-steering))
- VPP's own glean output (the ARP requests and neighbour solicitations it sends) bypasses guard, which polices kernel tc egress.
- Native XDP is refused on rvu-nicpf interfaces on kernels without upstream commit 04f647c8e456 (Linux 6.8), including the reference vendor kernel, where native attach panics. Use `generic` or `auto`.
- The .deb runs no maintainer scripts: run `systemctl daemon-reload` after every install.
- MCAM steering rules survived one vendor provisioning push on a lab box on one firmware release. Survival across firmware releases is untested. Nothing re-asserts stripped rules automatically; the 30 s readback reports them as `steering DEGRADED`.
